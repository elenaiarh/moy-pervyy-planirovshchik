# Техническое задание: локальный веб-планировщик задач «АССИЯ»

## 1. Назначение документа

Этот документ описывает функциональные, интерфейсные и технические требования к локальному MVP продукта «АССИЯ».

Задача документа — дать разработчику или нейросети-разработчику полное понимание того, что нужно реализовать, какие функции входят в продукт, какие сценарии должны поддерживаться, какие данные хранятся и какие ограничения нельзя нарушать.

## 2. Краткое описание продукта

«АССИЯ» — локальный браузерный планировщик задач для одной пользовательницы. Продукт помогает планировать день, неделю и месяц, видеть баланс между рабочими задачами, личными задачами «Я» и общими личными задачами «Мы», учитывать клиентов в рабочих задачах, работать с матрицей фокуса, напоминаниями и перегрузкой дня.

Продукт реализуется как веб-страница без backend, базы данных, авторизации и синхронизации. Все данные хранятся в браузере через `localStorage`.

## 3. Границы MVP

### Входит в MVP

- Локальная веб-страница.
- Один пользователь: владелица планировщика.
- Хранение данных в `localStorage`.
- Создание, просмотр, редактирование, удаление и выполнение задач.
- Представления: дашборд, день, неделя, месяц.
- Категории задач: «Рабочая», «Я», «Мы».
- Клиент как текстовое поле только для рабочих задач.
- Повторы: нет, каждую неделю, каждый месяц.
- Матрица фокуса из 4 квадрантов.
- Локальные напоминания в браузере.
- Возможность отложить напоминание.
- Фильтры по клиенту, матрице фокуса, категории, статусу, просрочке, повтору и наличию напоминания.
- Поиск по клиенту и дате.
- Аналитика по нагрузке, категориям, клиентам и выполнению.
- Ручной экспорт и импорт резервной копии задач в JSON.
- Предложение перенести задачи при перегрузе дня.
- Drag-and-drop перенос задач между датами в календаре.
- Мобильная адаптация.
- Русский язык интерфейса.
- Текущий визуальный стиль АССИИ как обязательный дизайн-гайд.
- PWA-режим: приложение можно установить на телефон и использовать почти как приложение.
- Тёмная тема в визуальном стиле АССИИ.

### Не входит в MVP

- Backend.
- База данных.
- Регистрация и авторизация.
- Несколько пользователей.
- Роли кроме владелицы.
- Клиент как отдельная сущность.
- Проекты внутри клиента.
- Пользовательские категории.
- Дополнительные поля задачи: описание, чеклист, ссылки, вложения, стоимость, место, комментарии.
- Статусы кроме «не выполнена» и «выполнена».
- Продвинутые повторы: ежедневно, по будням, произвольный интервал, повтор до даты.
- Внешние календари: Google Calendar, Outlook, Apple Calendar, `.ics`.
- Быстрое создание задачи кликом по дню календаря.
- Автопланирование.
- История изменений задачи.
- Архив завершённых задач.

## 4. Пользователь и роли

В MVP есть только одна роль: владелица планировщика.

Владелица может:

- создавать задачи;
- редактировать задачи;
- удалять задачи;
- отмечать задачи выполненными;
- просматривать задачи за день, неделю и месяц;
- фильтровать задачи;
- искать задачи;
- ставить напоминания;
- откладывать напоминания;
- переносить задачи между датами;
- смотреть аналитику;
- видеть перегруз дня и предложения по переносу.

Других ролей нет.

## 5. Техническая реализация

### Формат проекта

Проект остаётся локальной веб-страницей.

Текущая структура проекта сохраняется:

- `index.html` — HTML-оболочка;
- `src/styles.css` — стили;
- `src/app.js` — логика приложения;
- `package.json` — служебный запуск локального статического сервера;
- `README.md` — инструкция;
- `favicon.svg` — иконка;
- `concept.md` — концепция;
- `tz.md` — настоящее техническое задание.

Запрещено добавлять backend, серверную базу данных или внешнее API для хранения задач.

### PWA-режим

Приложение должно поддерживать PWA-режим.

Требования:

- приложение можно установить на телефон через браузер;
- приложение имеет manifest-файл;
- приложение имеет иконки для установки;
- приложение открывается в отдельном окне без лишней браузерной рамки, если платформа это поддерживает;
- базовые статические файлы приложения кэшируются для повторного открытия;
- данные продолжают храниться в `localStorage`;
- PWA не должна требовать backend или серверную базу данных.

Минимальные технические артефакты:

- `manifest.webmanifest` или эквивалентный manifest-файл;
- service worker для кэширования статических файлов;
- meta-теги темы и иконок в `index.html`.

### Хранение данных

Все данные хранятся в `localStorage`.

Основной ключ:

```text
assiya.tasks.v1
```

Значение — JSON-массив задач.

Дополнительные ключи допускаются только для UI-состояния, например:

```text
assiya.splash.done
assiya.settings.v1
assiya.theme.v1
```

### Ограничения `localStorage`

`localStorage` остаётся обязательным способом хранения для текущего MVP, потому что продукт должен быть локальной веб-страницей без базы данных и backend.

При этом разработчик обязан учитывать ограничения:

- не хранить в задачах тяжёлые вложения или бинарные данные;
- не записывать данные в `localStorage` на каждое мелкое движение мыши или drag-событие;
- выполнять запись только после осмысленного действия пользователя: создать, сохранить, удалить, перенести, выполнить, импортировать;
- держать структуру данных компактной;
- предусмотреть ручной экспорт JSON как защиту от потери локальных данных.

Использование `IndexedDB` не входит в текущий MVP. Его можно рассматривать только как будущую миграцию, если продукт выйдет за рамки локального MVP.

## 6. Дизайн-гайд

### Характер интерфейса

Интерфейс должен ощущаться как спокойный, заботливый и уверенный ассистент. Запрещены агрессивные предупреждения, резкие красные ошибки, мигающие уведомления и давящий тон.

### Визуальный стиль

Стиль обязателен:

- ретро-эстетика;
- печатная машинка;
- бумажные карточки;
- мягкие тени;
- сургучная печать;
- пастельные цвета;
- много воздуха;
- плавные анимации.

### Основные цвета

- Фон: `#F5E6D3`.
- Основной текст: `#2B3A4A`.
- Второстепенный текст: `#6B7A8A`.
- Акцент: `#C4A86C`.
- Рабочие задачи: `#D4B5B0`.
- Задачи «Я»: `#B5D4C0`.
- Задачи «Мы»: `#C4C7E8`.
- Просрочка: `#D4A090`.
- Свободное время: `#D9D0C4`.

### Тёмная тема

Тёмная тема обязательна.

Она должна сохранять характер АССИИ:

- не делать интерфейс резко чёрным;
- использовать глубокий графитово-синий фон;
- сохранить медно-золотой акцент;
- оставить различимыми категории «Рабочая», «Я», «Мы»;
- сохранить мягкие тени и ретро-эстетику;
- не использовать кислотные цвета.

Переключатель темы должен быть доступен в интерфейсе. Выбранная тема должна сохраняться в `localStorage`.

Ключ хранения:

```text
assiya.theme.v1
```

Допустимые значения:

```text
light
dark
```

### Тон текстов

Тексты должны быть поддерживающими:

- не «Срочно сделай», а «Эти задачи ждут твоего внимания»;
- не «Ты не успела», а «Ты просто перераспределяешь фокус»;
- не «Ошибка перегруза», а «Ты много запланировала. Давай посмотрим, что можно перенести».

## 7. Сущности данных

## 7.1. Task

Задача — основная сущность продукта.

Рекомендуемая структура:

```json
{
  "id": "uuid",
  "title": "Подготовить план проекта",
  "category": "work",
  "client": "Анна Смирнова",
  "date": "2026-07-20",
  "start": "09:30",
  "end": "10:45",
  "allDay": false,
  "repeat": "none",
  "focus": "urgentImportant",
  "care": true,
  "reminderAt": "2026-07-20T09:15",
  "reminderDone": false,
  "snoozedUntil": "",
  "completedDates": [],
  "recurrenceExceptionDates": [],
  "sourceTaskId": "",
  "createdAt": 1784544000000
}
```

### Поля задачи

| Поле | Тип | Обязательное | Описание |
|---|---:|---:|---|
| `id` | string | да | Уникальный идентификатор задачи |
| `title` | string | да | Название задачи |
| `category` | string | да | `work`, `self`, `together` |
| `client` | string | условно | Только для рабочих задач |
| `date` | string | да | Дата задачи в формате `YYYY-MM-DD` |
| `start` | string | условно | Время начала, если `allDay = false` |
| `end` | string | нет | Необязательное время окончания |
| `allDay` | boolean | да | Задача на весь день |
| `repeat` | string | да | `none`, `weekly`, `monthly` |
| `focus` | string | да | Квадрант матрицы фокуса |
| `care` | boolean | да | Предупреждать о перегрузе дня |
| `reminderAt` | string | нет | Дата и время напоминания |
| `reminderDone` | boolean | да | Напоминание уже сработало |
| `snoozedUntil` | string | нет | Время отложенного напоминания |
| `completedDates` | string[] | да | Даты выполненных повторений |
| `recurrenceExceptionDates` | string[] | да | Даты исключений из повторяющейся серии |
| `sourceTaskId` | string | нет | ID исходной повторяющейся задачи для одиночного изменения |
| `createdAt` | number | да | Timestamp создания |

### Обязательные поля при создании

Для всех задач обязательны:

- название;
- категория;
- дата;
- матрица фокуса;
- повтор;
- чекбокс заботы, по умолчанию включён.

Если задача не на весь день, желательно указать время начала. Время окончания необязательно.

Если `end` не заполнено:

- задача отображается в расписании как точка старта;
- задача не считается фиксированным временным блоком;
- задача не должна создавать или закрывать промежуток «Воздух»;
- просрочка в текущий день считается по `start`, а не по `end`.

Для рабочей задачи поле «Клиент» должно быть доступно. В MVP допускается сохранить рабочую задачу без клиента, но интерфейс должен мягко подсказать, что клиент помогает видеть нагрузку.

## 7.2. Категории задач

Допустимые значения:

```js
work      // Рабочая
self      // Я
together  // Мы
```

Старое значение `personal`, если встречается в сохранённых данных, должно автоматически мигрировать в `self`.

## 7.3. Матрица фокуса

Допустимые значения:

```js
urgentImportant // Важно + Срочно
important       // Важно + Не срочно
urgent          // Не важно + Срочно
calm            // Не важно + Не срочно
```

## 7.4. Повторы

Допустимые значения:

```js
none
weekly
monthly
```

Редактирование повторяющейся задачи работает только для одного повторения.

Правило реализации:

- если пользователь редактирует повторяющуюся задачу на конкретную дату, исходная серия не меняется;
- дата редактируемого повторения добавляется в `recurrenceExceptionDates` исходной задачи;
- создаётся новая одиночная задача с `repeat = "none"` и `sourceTaskId`, равным ID исходной задачи.

## 8. Экраны продукта

## 8.1. Splash Screen

Показывается при первом открытии сессии.

Содержит:

- медальон;
- букву «А»;
- название «АССИЯ»;
- мягкую анимацию появления.

После завершения открывается дашборд.

## 8.2. Дашборд

Дашборд — главный экран.

Должен показывать:

- логотип;
- дату;
- приветствие по времени суток;
- кольцевую диаграмму задач за выбранный день;
- количество задач по категориям «Рабочая», «Я», «Мы»;
- процент выполненных задач;
- аффирмацию под балансом;
- блок просрочки, если есть просроченные задачи;
- блок «Клиенты дня»;
- блок «Матрица фокуса»;
- переключатель «День / Неделя / Месяц»;
- мини-календарь на 7 дней;
- preview выбранного режима;
- кнопку добавления задачи.

### Кольцевая диаграмма

Кольцо должно показывать три сегмента:

- рабочие задачи;
- задачи «Я»;
- задачи «Мы».

В центре:

- общее количество задач за день;
- подпись «всего задач».

Внешняя аура показывает процент выполненных задач.

## 8.3. Экран дня

Экран дня показывает подробное расписание выбранной даты.

Должен содержать:

- кнопку возврата;
- заголовок даты;
- текущее время;
- фильтр матрицы фокуса;
- фильтр по клиенту;
- блок «Клиенты дня»;
- блок «Матрица фокуса»;
- активные задачи;
- все задачи дня в хронологическом порядке;
- блоки свободного времени «Воздух»;
- мотивирующую подпись внизу;
- кнопку добавления задачи.

### Активная задача

Задача считается активной, если:

- дата задачи совпадает с выбранной датой;
- задача не выполнена;
- задача на весь день;
- или текущее время находится между `start` и `end`, если оба времени заполнены;
- или `end` не заполнено, а текущее время находится после `start` в пределах текущего дня.

### Свободное время

Если между двумя задачами есть промежуток больше 30 минут, показывать блок:

```text
Здесь ты можешь выдохнуть
```

и диапазон времени.

## 8.4. Экран недели

Экран недели показывает выбранную неделю.

Должен содержать:

- заголовок недели;
- стрелки переключения недель;
- кнопку «Сегодня»;
- сетку 7 дней;
- до 3 задач в каждом дне;
- счётчик `+N`, если задач больше;
- цветные точки категорий;
- график нагрузки по дням.

График нагрузки должен показывать вклад категорий:

- рабочие;
- Я;
- Мы.

## 8.5. Экран месяца

Экран месяца показывает выбранный месяц.

Должен содержать:

- заголовок месяца;
- стрелки переключения месяцев;
- кнопку «Сегодня»;
- количество задач в месяце;
- сводку по категориям;
- самого активного клиента месяца;
- календарную сетку месяца;
- количество задач в каждом дне;
- первые задачи внутри дня;
- цветные маркеры категорий;
- переход в подробный день по клику на день.

В месяце запрещено обрезать круговые маркеры и счётчики задач. На узких экранах допускается горизонтальная прокрутка календарной сетки.

## 8.6. Модальное окно задачи

Открывается по кнопке добавления или при редактировании задачи.

Поля:

- название;
- категория: «Рабочая», «Я», «Мы»;
- клиент, только если категория «Рабочая»;
- дата;
- время начала;
- время окончания;
- «Весь день»;
- напоминание;
- повтор;
- матрица фокуса;
- чекбокс заботы о перегрузе;
- кнопка сохранения;
- кнопка удаления при редактировании.

При выборе категории «Я» или «Мы» поле клиента скрывается.

## 9. Функциональные требования

## 9.1. Создание задачи

Пользователь может создать задачу через кнопку `+`.

После сохранения:

- задача добавляется в `localStorage`;
- выбранная дата становится активной;
- пользователь видит мягкое подтверждение;
- если день перегружен, показывается предложение перенести часть задач.

## 9.2. Редактирование задачи

Пользователь может открыть задачу из списка дня и изменить её поля.

Если редактируется повторяющаяся задача, меняется только выбранное повторение.

## 9.3. Удаление задачи

Пользователь может удалить задачу из модального окна редактирования.

Если удаляется повторение повторяющейся задачи, удаляется только выбранная дата через `recurrenceExceptionDates`.

## 9.4. Выполнение задачи

Пользователь может отметить задачу выполненной.

Для обычной задачи дата добавляется в `completedDates`.

Для повторяющейся задачи выполнение фиксируется отдельно для конкретной даты.

Выполненная задача:

- становится визуально бледнее;
- перечёркивается;
- учитывается в прогрессе дня;
- отображается серой точкой в календарях.

## 9.5. Просрочка

Задача считается просроченной, если:

- она не выполнена;
- её дата меньше текущей даты;
- или дата равна текущей, `end` заполнено и `end` уже прошёл;
- или дата равна текущей, `end` не заполнено и `start` уже прошёл;
- задача не на весь день.

Просрочка отображается мягким терракотовым цветом.

## 9.6. Напоминания

В MVP напоминания работают локально в браузере.

Требования:

- пользователь может включить напоминание;
- пользователь выбирает дату и время;
- если браузер разрешает уведомления, показывается системное браузерное уведомление;
- если разрешения нет, показывается внутренний тост;
- после срабатывания `reminderDone = true`;
- если пользователь изменил время напоминания, `reminderDone` сбрасывается.

Ограничение должно быть явно показано в интерфейсе:

```text
Напоминания надёжнее всего работают, пока АССИЯ открыта в браузере или PWA. Если приложение закрыто или система выгрузила его из памяти, уведомление может не сработать вовремя.
```

Для гарантированных уведомлений в будущем потребуется backend или другой надёжный механизм доставки уведомлений.

### Будущие каналы

В ТЗ нужно заложить возможность будущих каналов, но не реализовывать их в MVP.

Потенциальные каналы:

- browser;
- email;
- Telegram;
- push.

Для MVP реализуется только `browser`.

## 9.7. Отложить напоминание

После срабатывания напоминания пользователь должен иметь возможность отложить его.

Варианты:

- через 10 минут;
- через 1 час;
- завтра утром.

Реализация:

- при выборе варианта заполнить `snoozedUntil`;
- `reminderDone` временно сбросить в `false`;
- следующее срабатывание проверять по `snoozedUntil`, если оно заполнено;
- после повторного срабатывания очистить `snoozedUntil`.

## 9.8. Перегруз дня

День считается перегруженным, если в нём больше 5 задач.

Если при создании или редактировании задачи день становится перегруженным и включён чекбокс заботы, приложение должно показать мягкое предупреждение и предложить перенести часть задач.

Предложение переноса:

- показать список задач дня;
- выделить задачи с низким фокусом, например «Не важно + Не срочно»;
- предложить ближайший день с меньшим количеством задач;
- пользователь сам подтверждает перенос.

Автоматически переносить задачи без подтверждения запрещено.

## 9.9. Drag-and-drop перенос задач

Пользователь может перетащить задачу на другой день в недельном или месячном календаре.

После переноса:

- меняется `date`;
- для повторяющейся задачи применяется правило редактирования одного повторения;
- задача сохраняется в `localStorage`;
- пользователь видит мягкое подтверждение.

На мобильных устройствах drag-and-drop не является основным способом переноса.

Обязательный мобильный паттерн:

- пользователь открывает задачу на редактирование;
- в модальном окне видит поле «Дата»;
- при нажатии на поле вызывается нативный календарь телефона;
- пользователь выбирает новый день;
- нажимает «Сохранить»;
- задача переносится на выбранную дату.

Дополнительная кнопка «Перенести» допустима, только если она открывает то же поле выбора даты и не дублирует отдельный сложный сценарий.

## 9.10. Фильтры

Обязательные фильтры:

- клиент;
- дата;
- категория;
- статус выполнения;
- просрочка;
- повтор;
- наличие напоминания;
- матрица фокуса.

Фильтры должны работать совместно.

Если после применения фильтров задач нет, показывать пустое состояние в поддерживающем тоне.

## 9.11. Поиск

Обязательный поиск:

- по клиенту;
- по дате.

Поиск по клиенту должен искать частичное совпадение без учёта регистра.

Поиск по дате должен позволять выбрать дату через поле даты или календарный контрол.

## 9.12. Аналитика

Аналитика должна быть локальной и рассчитываться на основе задач в `localStorage`.

Требование к производительности:

- дашборд не должен пересчитывать тяжёлую аналитику по всей истории задач;
- дашборд считает только показатели выбранного дня;
- экран недели считает только выбранную неделю;
- экран месяца считает только выбранный месяц;
- полная аналитика по всем данным рассчитывается только при открытии отдельного аналитического блока или экрана;
- тяжёлые метрики нельзя пересчитывать на каждый рендер без необходимости.

Обязательные показатели:

- количество задач за день;
- количество задач за неделю;
- количество задач за месяц;
- баланс категорий «Рабочая / Я / Мы»;
- количество выполненных задач;
- количество невыполненных задач;
- количество просроченных задач;
- нагрузка по клиентам за день;
- нагрузка по клиентам за неделю;
- нагрузка по клиентам за месяц;
- самый активный клиент месяца;
- самые загруженные дни месяца;
- процент выполнения за выбранный период.

Аналитика должна отображаться спокойно, без оценочного давления.

## 9.13. Экспорт и импорт резервной копии

Для локального приложения экспорт и импорт JSON входят в MVP.

### Экспорт

Пользователь может скачать резервную копию данных.

Требования:

- экспорт создаёт `.json` файл;
- файл содержит все задачи из `localStorage`;
- файл содержит версию формата данных;
- файл содержит дату экспорта;
- файл не должен содержать ничего, кроме данных приложения АССИЯ.

Рекомендуемая структура файла:

```json
{
  "app": "assiya",
  "version": 1,
  "exportedAt": "2026-07-20T12:00:00.000Z",
  "tasks": []
}
```

### Импорт

Пользователь может загрузить ранее экспортированный JSON-файл.

Требования:

- перед импортом приложение проверяет, что файл относится к АССИИ;
- приложение проверяет наличие массива `tasks`;
- при ошибке показывает мягкое сообщение;
- импорт не должен молча уничтожать текущие данные;
- пользователь должен выбрать режим импорта:
  - заменить текущие данные;
  - объединить с текущими данными.

При объединении:

- задачи с уже существующими `id` не дублируются;
- новые задачи добавляются;
- после импорта данные сохраняются в `localStorage`.

## 11. Бизнес-правила

1. Приложение не должно требовать интернет для хранения и чтения задач.
2. После перезагрузки страницы задачи должны сохраняться.
3. Рабочая задача может иметь клиента, но клиент не является отдельной сущностью.
4. Категории фиксированные: «Рабочая», «Я», «Мы».
5. Пользовательские категории запрещены.
6. Статусы только два: выполнена и не выполнена.
7. Просрочка вычисляется автоматически.
8. Повторяющаяся задача при редактировании меняется только на выбранную дату.
9. Удаление повторения не должно удалять всю серию.
10. Drag-and-drop перенос не должен выполняться без сохранения в `localStorage`.
11. Автопланирование запрещено.
12. Внешние календарные интеграции запрещены.
13. Интерфейс должен оставаться мягким и поддерживающим.
14. Тёмная тема не должна менять функциональность приложения.
15. PWA-режим не должен менять способ хранения данных: задачи остаются в `localStorage`.

## 12. Адаптивность

Мобильная адаптация обязательна.

Приложение проектируется mobile-first: все основные действия должны быть доступны на телефоне без горизонтального скролла, кроме месячной календарной сетки, где горизонтальная прокрутка допустима для сохранения 7 колонок.

### Мобильная версия

- Все основные блоки растягиваются на ширину экрана.
- Кольцо баланса и легенда располагаются вертикально.
- Модальное окно открывается снизу.
- Месяц может иметь горизонтальную прокрутку, если 7 колонок не помещаются.
- Круговые маркеры и счётчики в месяце не должны обрезаться.
- Drag-and-drop должен иметь альтернативу через действие «Перенести».

### Десктопная версия

- Кольцо и легенда располагаются горизонтально.
- Неделя и месяц используют сетки.
- Модальное окно открывается по центру.
- Наведение на кнопки даёт мягкую тень.

## 12.1. PWA-сценарий

Пользователь должен иметь возможность установить приложение на телефон.

Сценарий:

1. Владелица открывает приложение в браузере телефона.
2. Браузер предлагает установить приложение или позволяет выбрать «Добавить на экран Домой».
3. После установки приложение открывается как отдельное приложение.
4. Задачи остаются доступными, потому что данные хранятся локально.

## 12.2. Сценарий тёмной темы

Владелица может переключить тему интерфейса.

Сценарий:

1. Пользователь открывает переключатель темы.
2. Выбирает светлую или тёмную тему.
3. Интерфейс меняет палитру.
4. Выбранная тема сохраняется после перезагрузки страницы.

## 13. Пустые состояния

Пустые состояния должны быть поддерживающими.

Примеры:

- «У тебя есть свободное время. Наслаждайся паузой или добавь что-то важное.»
- «В этом месяце пока много воздуха. Можно спокойно выбрать, что важно.»
- «По этим фильтрам задач нет. Можно мягко расширить поиск.»

## 14. Ошибки и валидация

Ошибки не должны быть агрессивными.

Валидация:

- нельзя сохранить задачу без названия;
- нельзя сохранить задачу без даты;
- если `allDay = false`, время начала желательно и должно быть доступно для заполнения;
- время окончания необязательно;
- если время окончания заполнено, оно не должно быть раньше времени начала;
- если напоминание включено, дата и время напоминания должны быть заполнены;
- если клиент не указан у рабочей задачи, показать мягкую подсказку, но не блокировать сохранение.

## 15. Критерии приёмки

### Хранение

- После создания задачи она появляется в интерфейсе.
- После перезагрузки страницы задача остаётся.
- После редактирования задача обновляется в `localStorage`.
- После удаления задача исчезает из интерфейса и `localStorage`.
- Пользователь может скачать JSON-резервную копию.
- Пользователь может импортировать JSON-резервную копию.
- Импорт с ошибочным файлом не должен ломать текущие данные.

### Категории

- В форме есть категории «Рабочая», «Я», «Мы».
- При выборе «Рабочая» появляется поле клиента.
- При выборе «Я» или «Мы» поле клиента скрывается.
- В кольце баланса категории считаются отдельно.
- В неделе и месяце категории отображаются разными цветами.

### Клиенты

- Клиент сохраняется как текстовое поле задачи.
- Клиенты дня считаются по рабочим задачам.
- Фильтр по клиенту показывает только задачи выбранного клиента.
- Самый активный клиент месяца определяется по количеству задач.

### Матрица фокуса

- У каждой задачи есть один квадрант матрицы.
- На дашборде и в дне видны количества по квадрантам.
- Клик по квадранту фильтрует задачи.

### Напоминания

- Напоминание можно включить и выключить.
- Напоминание сохраняется.
- Напоминание срабатывает локально.
- Напоминание можно отложить на 10 минут, 1 час или завтра утром.
- В интерфейсе есть честное предупреждение, что локальные напоминания могут не сработать вовремя, если приложение закрыто или выгружено системой.

### Повторы

- Доступны повторы: нет, каждую неделю, каждый месяц.
- Выполнение повторяющейся задачи фиксируется отдельно по датам.
- Редактирование повторяющейся задачи меняет только выбранное повторение.

### Календарь

- День показывает задачи выбранной даты.
- Неделя показывает 7 дней.
- Месяц показывает календарную сетку месяца.
- Клик по дню месяца открывает подробный день.
- В месяце не обрезаются кружочки и счётчики задач.
- Drag-and-drop переносит задачу на новую дату.
- На мобильном перенос доступен через поле «Дата» в модальном окне редактирования задачи.

### Фильтры и поиск

- Фильтры по клиенту, дате, категории, статусу, просрочке, повтору, напоминанию и матрице работают.
- Фильтры можно комбинировать.
- Поиск по клиенту работает по частичному совпадению.
- Поиск по дате открывает задачи выбранного дня.

### Аналитика

- Аналитика показывает баланс категорий.
- Аналитика показывает выполненные и просроченные задачи.
- Аналитика показывает нагрузку по клиентам.
- Аналитика показывает самые загруженные дни.
- Дашборд не пересчитывает тяжёлую аналитику по всей истории задач.

### PWA

- Приложение имеет manifest-файл.
- Приложение имеет service worker.
- Приложение можно установить на телефон.
- После установки приложение открывается без потери задач.
- Данные по-прежнему хранятся в `localStorage`.

### Тёмная тема

- В интерфейсе есть переключатель светлой и тёмной темы.
- Тёмная тема сохраняется после перезагрузки.
- Все тексты, кнопки, карточки, календарные точки и диаграммы остаются читаемыми.
- Цвета категорий «Рабочая», «Я», «Мы» остаются различимыми.

## 16. Что нельзя добавлять без отдельного решения

Разработчик не должен добавлять:

- backend;
- серверную базу;
- авторизацию;
- роли;
- клиентскую CRM;
- проекты;
- пользовательские категории;
- внешние календари;
- автопланирование;
- историю изменений;
- архив задач;
- платные тарифы;
- английский интерфейс.

## 17. Итоговое ожидание

На выходе должен получиться локальный веб-планировщик «АССИЯ», который работает в браузере, хранит данные в `localStorage`, помогает владелице планировать день, неделю и месяц, видеть нагрузку по категориям, клиентам и матрице фокуса, получать напоминания, переносить задачи и не перегружать себя.

Главное ощущение продукта: спокойный контроль без давления.
